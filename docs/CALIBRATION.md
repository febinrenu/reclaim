# Calibrating the synthetic economy against published reality

Every probability and every rupee this project reasons about is generated by
`scripts/data/dgp.py` and priced by `scripts/data/reward.py`/`src/domain/scenario/*.ts`.
That is a limitation stated everywhere else in this repository, and stating it once more
does not answer the next question a reviewer actually has: **are these numbers even in the
right neighbourhood, or arbitrary?**

This document answers that directly, one parameter at a time, against a real published
source rather than intuition. Some numbers hold up. At least one does not, and that is
reported the same way a bad model-comparison result is reported elsewhere in this project
— found, stated, not quietly adjusted to look better after the fact.

Every figure below was looked up on 2026-08-29, cited to a specific page rather than a
vague "industry sources say."

## The one real divergence, in more depth

**The generator's failure mix is harder to recover than real card declines.** Real-world
data says 80–90% of card failures are the "soft," recoverable kind — a temporarily declined
card, a bank flag, insufficient funds at that instant. This project's `ERROR_CATEGORY_WEIGHTS`
gives `insufficient_funds` + `soft_decline` a combined 55%, with the harder categories
(`hard_decline`, `gateway_error`, `do_not_honor`) making up the other 45% — roughly triple
the real-world hard-decline share.

**What this does to the numbers already published elsewhere in this repository:** a harder
failure mix directly suppresses the achievable recovery rate, which is exactly the axis
`docs/RESULTS.md`'s Bayes-optimal-ceiling section already reports as a real constraint
(ROC-AUC ceiling 0.7831, not 1.0). It does not invalidate the *comparative* results — every
policy in the OPE bracket, and the 1.42× headline, is evaluated against the same generator,
so a harder-than-real failure mix suppresses every policy's absolute recovery rate roughly
equally rather than favouring one policy over another. What it means is that **the absolute
rupee figures in this README (₹347.93/txn, etc.) likely understate what a real merchant's
mix would produce**, since a real population has more of the easy, soft-decline money on the
table than this synthetic one does.

**What would fix it:** re-weighting `ERROR_CATEGORY_WEIGHTS` toward the published 80/20 split
and re-running `npm run data:generate && npm run scorer:train && npm run ope` end to end.
Not done here, deliberately: changing a generator parameter *because a review document said
to* without re-deriving every downstream number (the trained coefficients, the calibration
curve, the OPE bracket, the escalation-budget sweep) would make this document responsible
for a number nobody re-verified, which is the exact failure mode `docs/EVALUATION.md`'s
opening section warns against. Flagged here as the next real step, not silently applied.

## What this document is not

It is not a claim that the synthetic data is now validated. It is one specific, narrower
claim: **every major cost and rate constant in this project's economy was checked against a
real published number, in the open, rather than asserted from intuition** — and the one
place that check failed is named, quantified, and left unfixed rather than quietly patched
to pass.
